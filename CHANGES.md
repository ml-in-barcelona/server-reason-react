# Changes

## Unreleased

* Router: the generator names a path parameter used twice in one route path, `path parameter id appears more than once in /orgs/:id<int>/members/:id<string>`, and a loader label that repeats a path parameter or another loader label, where all three reported `duplicate branch input label` by @davesnx
* **Breaking**: Router: `RouterServer` is one flat module with the API an application or HTTP adapter uses, and the modules that generated code calls move to `RouterEngine`, which is not a stable API. `RouterServer.Render.notFound`/`redirect` and `RouterServer.Action.redirect` become `RouterServer.notFound` and one `RouterServer.redirect`, which works in render code and in server functions (`RouterServer.Signal` replaces `Action.Redirect`). `Request.key`/`memo`/`scope` become `RouterServer.memoKey`/`memo`/`requestScope`. `RouterServer.Adapter.*` functions move to the top (`RouterServer.serve`, `handle`, `parseRequest`, `response`, `reply`, `methodReply`, `formActionReply`, `serveFormAction`, `runFormAction`, `redirectLocation`, `actionRedirectHeader`, `metadataElement`), and `Server.clientRoot`, `clientRootWith` and `basePath` too. `Server.t` is `RouterServer.t`. `Server.clientRootWithCache` is `clientRoot ?pageCacheCapacity`, and `Adapter.document_element`, `full_model`, `patch_model` and `redirect_model` are no longer exported. Every `...WithContext` pair is one function that takes `~context`: `serve` and `handle` take a function, built inside the request cache only when the router runs, and `run`, `formActionReply` and `serveFormAction` take the value; pass `~context:(fun () -> ())` or `~context:()` for a manifest without `~context`. `RouterServer.run` takes the request from `parseRequest`. `DreamRouter.routesWithContext` is `DreamRouter.routes ~context`, which takes `fun _ -> ()` without a context. `RouterRuntime` keeps destinations, `PrefetchLevel`, `Status`, `Loader`, `Error`, `Metadata`, `Headers` and the navigation types; the search decoders (`RouterEngine.SearchValues`), `CatchAll`, patterns, `encodeSearch`, shallow search keys, the navigation state machine and `NavigationResponse` move to `RouterEngine`, and `RouterRuntime.Link` is gone by @davesnx
* **Breaking**: Router: URLs are printed with `Js.Global.encodeURIComponent` on native and in the browser, so both print the same bytes. A search value or hash that is not valid text (invalid UTF-8 on native, a lone surrogate in the browser) raises `Invalid_argument` from `href` and `destination`, where native printed `%FF` and the browser printed U+FFFD. Every generated route has `tryDestination` and `tryHref`, also without path parameters. The client no longer handles a link whose path has an encoded slash, a `.` or `..` segment, a control character or invalid UTF-8, which the server rejects, and a link is current or active by the same decoding as the route: a pair with a malformed escape is dropped by @davesnx
* Js: native `Js.Global.encodeURIComponent` and `encodeURI` raise `Invalid_argument "URI malformed"` for invalid UTF-8, as JavaScript throws `URIError` for a lone surrogate by @davesnx
* Router: user names in the route manifest no longer collide with the generated code. Path parameters and loader results named like generated helpers (`searchValues`, `tryDestination`, `value`, `pattern`, `input`, ...) compile, a route named like a module the generated code uses (`Stdlib`, `Fun`, `React`, `Js`, `RouterRuntime`, a codec module) no longer hides it, and a free name in a `Router.Search.default`, `~metadata`, `~headers`, redirect `~target` or `~errorStatus` expression keeps its meaning instead of picking up a path parameter of the same name. The hand-kept list of reserved labels is gone: the generator reports a conflict only where a user label meets a label that the router passes in the same call, and route names `Search` and `Link` are allowed. `_` and keywords are rejected as path parameter names by @davesnx
* Router: the navigation protocol version is 1 again by @davesnx
* **Breaking**: Router: a route path can have at most five optional segments. Each one doubles the patterns a route matches, and ten produced 12 MB of generated code. The generator rejects a sixth and suggests one route per shape or `~search` by @davesnx
* Router: fix route matching when a shorter route sits on the path to a more specific one. With `/docs/:rest<string...>`, `/docs/:version<string>/changes`, `/:lang<string>/:page<string>` and `/:lang<string>/:page<string>/edit`, the pathname `/docs/intro` matched `/:lang<string>/:page<string>` instead of the catch-all, which has more static segments by @davesnx
* Router: `RouterPattern.matchesPath` rejects the segments the server rejects (invalid UTF-8, an encoded `/`, control characters and dot segments), so the client no longer follows a redirect to such a URL as a route navigation. The parser rejects the path parameter name `_`, which generated invalid OCaml by @davesnx
* ReactDOM: `renderToStream` runs each component inside the `Lwt` values of its enclosing context providers, as `ReactServerDOM` already did, so an async component reads the right context value with `useContext` after a `let%lwt` wait, where it read the default value. The value belongs to the component's own promise chain, so renders that run at the same time each read their own value by @davesnx
* ReasonReactRouter: the native `ReasonReactRouter.ServerUrl` component provides the request URL to a server render, `<ReasonReactRouter.ServerUrl url="/books/1?sort=asc#top"> app </ReasonReactRouter.ServerUrl>`. Inside it, `useUrl ()` and `dangerouslyGetInitialUrl ()` return that URL split like the browser router (`path = ["books"; "1"]`, `search = "sort=asc"`, `hash = "top"`), also in async components after they suspend, with `renderToStream` and `render_model`. The closest provider wins, and an explicit `~serverUrl` or `~serverUrlString` still wins over it. Without a provider they return an empty URL, as before by @davesnx
* Router: a navigation that changes a route's own search parameters answers a patch that keeps the root and group layouts, where any change of the search string answered a full response. A layout scope is shared when its path parameters and the raw values of the search parameters in its reach (the root parameters for the root and its groups) are unchanged; the route itself is always rendered again, and a change of a root parameter still renders the whole page. A root or group loader must read search through `~search`, not from the raw request through `~context` by @davesnx
* **Breaking**: Router: `RouterServer.Branch.Scope.make` takes `~search`, the raw values of the search parameters in the scope's reach by URL key, and `RouterServer.Decode.searchValues ~input names` reads them. They do not enter `instanceKey`. Pass `~search:[]` for a scope with no search parameters in reach by @davesnx
* Router: search parameters take `~shallow:true`. A `navigate` or `Link` to the committed path that changes only shallow parameters of the destination's route updates the URL without a request, like `updateSearch`. Generated destinations carry the keys (`RouterRuntime.shallowSearch`, `RouterRuntime.withShallowSearch`), and the flag is part of the registry fingerprint by @davesnx
* Router: `Router.useUpdateSearch` and `Router.Route.useUpdateSearch` update the search from its latest value, `updateSearch(search => {...search, page: 1})`, so two updates in one handler both apply. For a record with a `required` field the update takes `option(search)`, as `useSearch` returns it. `RouterReact.useUpdateSearchWith` is the untyped form. A second `Push` search update in the same task replaces the entry the first one pushed by @davesnx
* Router: the client renders each navigation's new page inside React `startTransition`, so the old page stays on screen and interactive while the request runs and while new content without its own `~loading` streams in, where the nearest existing `Suspense` fallback, often the root `~loading`, replaced it. The URL, the history entry, the location the next navigation patches against and the `navigate` result change only when the new page is on screen, and the navigation status stays `Loading` until then. A navigation, search update or hash update that starts in that time cancels the waiting page and applies to the page on screen. With `~viewTransitions=true` a navigation still commits at once, unless the user prefers reduced motion, in which case no view transition runs by @davesnx
* Router: `RouterReact.useIsPending destination` is true while a navigation to the destination is in flight, and the provider sets `data-router-pending` on matching `Link`s during it, also on links in layouts that a patch keeps and in server components by @davesnx
* Router: `RouterReact.Link ~activeWhen` and `RouterReact.useIsActive ~activeWhen destination` choose when a destination is active: `Url` (same path and search, the `Link` default and the `useIsCurrent` rule), `Route` (same path with any search, the `useIsActive` default) or `Subtree` (the path or a path below it, by whole decoded segments). `aria-current` and the `data-router-link` marking after patches follow the link's rule by @davesnx
* Router: a `data` name on `RouterReact.Link` and an `attrs` name on `Router.Metadata.link` that is not made of ASCII letters, digits, `_`, `.`, `:` and `-` is dropped, on the server and in the browser. A name such as `"x onfocus=alert(1) y"` wrote extra attributes into the server HTML by @davesnx
* Router: `RouterServer.Adapter.serveFormAction` and `serveFormActionWithContext` render the page after a failed form post without JavaScript with render signals, as `serve` does, and `DreamRouter.routes` uses them. `RouterServer.Request.scope` always opens a new cache, so a scope around server start-up cannot share memoised entries between requests by @davesnx
* Router: `~loaderParallel=true` next to `~loader` on `Router.make`, `Router.group` and `Router.route` starts that loader together with its ancestor loaders instead of after them. It receives the path parameters, `~search` and `~context`, but no ancestor loader result. Results are still read parent-first, so an ancestor failure or redirect wins over a parallel loader that failed first, and the parallel loader's result is dropped then. The generator rejects `~loaderParallel` without `~loader` and a value that is not `true` or `false`. `RouterServer.Execution.start` and `Execution.await` run the generated code by @davesnx
* Router: `RouterServer.Request.memo key argument run` runs `run` once per request for each key and argument and shares the promise, like React's `cache`. `Request.key ()` makes a typed key and `Request.scope` opens a request. Every adapter entry point opens a new scope for its request. `Adapter.serve` and `serveFormAction` keep it for the whole response, including streamed server components, and `DreamRouter` uses them; `Adapter.handle`, `Adapter.handleWithContext` and the `formActionReply` functions cover loaders, `~metadata` and `~headers` only. Generated loaders are not memoised by @davesnx
* Router: an element with `data-router-scroll="<id>"` keeps its scroll position across history entries. The router saves it with the window position (when a navigation, `updateSearch` or `updateHash` leaves an entry, and on `pagehide`) and restores it on Back and Forward and after a reload. A new navigation does not move it. Positions saved by an earlier version still restore the window by @davesnx
* Router: an exception while a routed page renders in the browser, including content that streams in after a client navigation, shows an error boundary instead of unmounting the app. Each scope with `~error` gets a client boundary inside its layout, around its outlet; its fallback is the scope's `~error` component with `Internal({diagnosticId: "render"})`, rendered on the server with the page. Every routed payload also has a root boundary with the built-in "Something went wrong" text. A boundary shows its content again after the next content navigation. `RouterReact.errorBoundary` is the boundary by @davesnx
* Router: render code can answer not found or redirect. `RouterServer.Render.notFound ()` and `RouterServer.Render.redirect ?permanent destination` raise a signal; the new `RouterServer.Adapter.serve` and `serveWithContext` (`handle` and `response` in one step) render the HTML shell or the first chunk of a navigation payload before they reply, so a signal raised by then answers 404 with the route's not-found boundary or a redirect. A signal raised in content that streams later keeps the status and shows the nearest error boundary. Another exception in the HTML shell renders the route's nearest `~error` boundary with status 500. `DreamRouter.routes` uses `serveWithContext`. `Router.Error.notFoundReason` gains `RenderNotFound` by @davesnx
* Router: `Router.Status` gains `Unauthorized` (401), `Gone` (410), `TooManyRequests` (429) and `ServiceUnavailable` (503) for `~errorStatus` by @davesnx
* **Breaking**: Router: client hooks return values instead of raising. `Router.useRoute` returns `None` for a route id or path parameters it cannot decode, where it raised `Invalid_argument`. `RouterRuntime.Search.required` returns an option, and `Router.useSearch` and `Router.Route.useSearch` return `option(search)` when the record has a `required` field: `None` when the current URL lacks the value or it does not parse, for example while another route is active. Routes with path parameters get `Router.Route.tryDestination` and `tryHref`, which return `Error(message)` for a value no path segment can carry (empty, `/`, `.`, `..`, control characters) where `destination` and `href` raise by @davesnx
* Router: more hooks on the generated module. `Router.useMatches ()` returns every active route, outermost first, decoded like `useRoute`; `RouterReact.useMatches` returns them undecoded. `Router.useActiveSearch ()` returns the active route with its search record as `Router.ActiveSearch.t`, without naming the route. `Router.useLocation`, `useIsCurrent`, `useBlocker` and `useInvalidate` re-export the `RouterReact` hooks. `RouterRuntime.absoluteHref ~origin destination` joins an origin and an href. `ActiveSearch` is a reserved route name by @davesnx
* Router: `RouterReact.Link` takes `~style`, `~data` (rendered as `data-<name>` attributes) and `~anchorRef`. Generated route links take `~attributes`, built with `RouterReact.Link.attributes(~id, ~title, ~rel, ~ariaLabel, ~style, ~data, ~anchorRef, ~onClick, ~onMouseEnter, ())`, so an anchor `id` no longer clashes with a path parameter named `id`. `attributes` is a reserved label by @davesnx
* Router: the optional library `server-reason-react.dream` installs `DreamRouter`, the Dream adapter that was only in the demo, with the same API. Dune builds it only when Dream is installed, so `server-reason-react` still does not depend on Dream. `DreamRouter.routes` now stops rendering an HTML document after 30 seconds, the limit navigation responses already had. The router path is no longer normalised by Dream: it reaches the engine as sent, which decodes each segment when it matches, so a path with a malformed escape such as `/app/%ZZ` answers 400 instead of 404 by @davesnx
* Router: `RouterServer.Adapter.handle` and `handleWithContext` answer one request from its method, target and header list, `Adapter.parseRequest` reads the router request headers in any letter case into a `ServerEngine.request` and a prefetch level, and `Adapter.response` adds the transport headers to a reply and streams its HTML document or Flight model through a chunk writer. An adapter for another HTTP server only passes the request in and writes the response out. `DreamRouter` is built on them by @davesnx
* Router: `~pageCacheMaxAge` on `Router.make` (a float literal) and `?pageCacheMaxAge` on `Server.make` and `Server.makeWithContext` reach the client `Provider` through the client root, so an application does not need its own client root to keep pages fresh for a while by @davesnx
* **Breaking**: Router: the `make` given to `Server.clientRootWith` receives `~interceptLinks`, `~viewTransitions`, `~pageCacheCapacity` (an option) and `~pageCacheMaxAge` (an option), and `clientRootWith` takes `?pageCacheCapacity`. Add the four labels to a custom `make` and pass them to `RouterReact.Provider` by @davesnx
* Router: `Router.Search.required`, `optional`, `default` and `many` take `~key:"..."`, the URL key of the parameter when it differs from the record field name, for example `infoPage = Router.Search.optional ~key:"info-page" string`. The record field and constructor argument keep the label; hrefs, destinations, server and client decoders, the `useSearch` update and the registry fingerprint use the key. The generator rejects an empty key, a key that is not valid UTF-8 or not a string literal, two parameters of one branch with the same key (root parameters included), and any other labelled argument on a search constructor by @davesnx
* Router: `navigate`, a `Link` or an intercepted click to the committed URL (path, search in any order, and hash) without `~revalidate=true` does nothing and resolves to `Committed` with the committed location, where it added a history entry and ran a full navigation. While a navigation to another URL is in flight, it still runs and replaces that navigation. A server function redirect to the current page still navigates by @davesnx
* Router: the functions from `useNavigation`, `useSearch`, `useUpdateHash` and `useInvalidate` keep their identity for the provider's lifetime, where they changed on every navigation and search update. The generated `Router.useSearch` and `Router.Route.useSearch` update functions and the `useBlocker` result keep theirs while the component stays mounted and the held navigation is the same by @davesnx
* Router: a request context for loaders, `~metadata` and `~headers`. `Router.make ~context=Session.t` names its type, the generated registry passes `~context` to every loader, `~metadata` and `~headers` function, and `RouterRegistry.server` comes from the new `Server.makeWithContext`. Run it with the new `RouterServer.runWithContext ~context` (also `ServerEngine.runWithContext`, `Adapter.formActionReplyWithContext`, `Endpoint.executionWithContext`, and the demo `DreamRouter.routesWithContext ~context:(Dream.request -> 'context)`). A manifest without `~context` generates the same code as before, and `RouterServer.run`, `Server.make`, `formActionReply` and `DreamRouter.routes` keep their arguments. The generator rejects `~context` on a group, route or redirect, and a path parameter or loader label named `context` when the manifest declares `~context` by @davesnx
* **Breaking**: Router: `Endpoint.t`, `Endpoint.prepared`, `EndpointRegistry.t`, `EndpointRegistry.matched` and `Server.t` take the context type as a third type parameter, `unit` for a server from `Server.make`. An endpoint's `~execution` receives the context as its argument, `()` without one, so existing `fun () -> ...` executions still type-check. Only type annotations change, for example `(plan, string) Endpoint.t` becomes `(plan, string, unit) Endpoint.t` by @davesnx
* Router: a route that adds search parameters to the root ones gets `Router.Route.useSearch`, with the route's search record and an update function that owns the root and route names. It decodes with the same rules as the server and updates the URL without a request, like `Router.useSearch` by @davesnx
* **Breaking**: Router: the server entry point is `RouterServer.run` instead of `RouterServer.Server.run`, with the same arguments by @davesnx
* Router: `~revision` is optional on `RouterServer.run`, `ServerEngine.run` and `Adapter.formActionReply`. Without it every response carries the revision `""`, for an application that does not track deploys by @davesnx
* Router: a reload or a return to the page from another document shows the saved scroll position from the first frame. The client sets `history.scrollRestoration` to `auto` on `pagehide`, so the browser restores the position before the router hydrates, and back to `manual` when the page comes back from the back/forward cache by @zakybilfagih
* **Breaking**: Router: `navigate`, `RouterReact.Link` and the generated route `Link`s take `~resetScroll` (default `true`). With `~resetScroll=false` a `Push` or `Replace` keeps the scroll position and focus instead of scrolling to the top and focusing `#router-focus-root`, for navigations that update the page in place, such as a refresh after a server function. A hash in the destination still scrolls to its element, and Back and Forward still restore saved positions. A path parameter cannot be called `resetScroll`, because the generated route `Link` takes it by @zakybilfagih
* **Breaking**: Router: search parameters reach the generated API as one record instead of one labelled argument each. `Router.search` holds the root parameters, and each route with search parameters has `Router.Route.search` with the root fields and its own (a route without its own re-exports `Router.search`), a constructor `Router.Route.search(~name=?, ...)`, and `search_to_rsc` and `search_of_rsc` for client component props. `destination`, `href` and the route component take `?search` (`~search` when a parameter is required); pages, layouts, loaders, metadata, headers, boundaries and redirect targets receive `~search`; the `useSearch` update function takes a whole record. Search parameter names no longer collide with generated arguments, so `target`, `error`, `input`, `hash`, `value` and `pattern` are valid; `routeSearch` is a new reserved label for path parameters and loader results. A record literal in a JSX prop needs the generated interface: generate `Router.mli` with `--mode interface`. A library that compiles the generated `Router.ml` now depends on `server-reason-react.rsc` or `server-reason-react.rsc-native` by @davesnx
* **Breaking**: Router: `Router.group` no longer takes `~search`. The generator rejects it with a router error. Declare shared search parameters on `Router.make`, or on each route by @davesnx
* **Breaking**: Router: the root `~error` of `Router.make` is a boundary component, as on groups and routes, and its module no longer needs a `status` function. The new `~errorStatus` on `Router.make` maps an application error to a `Router.Status.t`; without it an application error answers 500. Move `~error=AppError` with `AppError.status` to `~error=AppError, ~errorStatus=AppError.status` by @davesnx
* **Breaking**: Router: `~loaderAs_` is renamed `~loaderLabel`, and `Router.redirect ~to_` is renamed `~target`. The old labels give a router error that names the new label by @davesnx
* Router: progressive-enhancement forms on page routes. A server-function form posted without JavaScript runs its function and answers 303 to the same page (post/redirect/get), or to the destination given to the new `RouterServer.Action.redirect`. A call from JavaScript that ends with `RouterServer.Action.redirect` gets a `null` action result and a `Router-Redirect: <href>` header. The reply to a form post is never 307 or 308: when the page redirects, for example on a URL with a trailing slash, it is a 303. A multipart `POST` without a `$ACTION_ID_` field still reaches the `~actionHandler` with its body intact. A failure renders the page with the route's nearest `~error` boundary and status 500. `RouterServer.Adapter.runFormAction` and `formActionReply` hold the shared parts, `RouterServer.run ?actionError` and `Plan.withFailure` render the failure, and the demo `DreamRouter.routes ~lookup` wires them for multipart posts without an `ACTION_ID` header by @davesnx
* **Breaking**: Router: a wrong query string renders the page and ignores the wrong part, where it answered 400. `Search.parse` ignores empty pairs, as in `?a=1&&b=2&`, and drops a pair with a malformed escape or a key or value that is not valid UTF-8 after percent-decoding, such as `?q=%FF`; the other pairs are read. A value that its parser rejects reads as `None` for an `optional` parameter and as the default for a `default` one, and a `many` parameter skips it. A `required` parameter that is missing or rejected still answers 400 with `InvalidSearchParameter`, and so does a query over 8192 bytes. Server and client decode the same way. `Search.error` and `RouterQuery.error` lose `MalformedEscape` by @davesnx
* Router: the server compares the base path with the request path segment by segment after percent-decoding, as route segments are compared, so `/m%c3%bcnchen/notes` matches the base path `/m%C3%BCnchen`, and `/app` still does not match `/apple` by @davesnx
* Router: add `RouterServer.Adapter.methodReply ~allow method_`. `OPTIONS` answers 204 and a method outside `allow` answers 405, both with an `Allow` header. The demo `DreamRouter.routes` answers `HEAD` like `GET` without a body, `OPTIONS` with 204 and other methods with 405, where Dream answered 404 by @davesnx
* Router: the demo `DreamRouter.routes` checks `Origin` (or `Referer`) against `Host` on server function `POST`s with `Dream.origin_referrer_check`, and its default `diagnosticId` and `revision` come from `Dream.random` instead of the unseeded `Random.bits` by @davesnx
* Router: `~metadata` and `~headers` of all scopes start at once instead of one scope after the other. They still merge from the root down by @davesnx
* **Breaking**: Router: per-route prefetch levels. `Router.route` and `Router.group` take `~prefetch=Off|Intent|Viewport|Idle` (default `Intent`, inherited by children). `RouterRuntime.prefetchLevel` reads the level of a destination, and `RouterRuntime.PrefetchLevel` names the levels. `RouterServer.run ?prefetch` handles a request with `Router-Prefetch: <level>`: a level more eager than the route's gives the new outcome `PrefetchRefused level`, which `Adapter.reply` answers with 204 and `Router-Prefetch-Refused`, and runs no loader; an accepted prefetch answers as a navigation. Every RSC reply carries `Vary: Accept, Router-Prefetch`. Matches on `ServerEngine.outcome` must handle `PrefetchRefused` by @davesnx
* Router: add `DreamRouter.request`, the Dream request of the current response. Route loaders, `~metadata`, `~headers` and server components read their own request after any `Lwt` wait and during streaming, also when requests run at the same time by @davesnx
* **Breaking**: Router: the client root receives `routes`, every concrete route path without the base path (`Server.routes`), and `RouterPattern.matchesPath ~basePath` tells whether a URL path has the shape of a route. The `make` function given to `Server.clientRootWith` takes a new `~routes` argument by @davesnx
* Router: `Router.make` takes `~interceptLinks` and `~viewTransitions`, and `Server.make` takes `?interceptLinks` and `?viewTransitions`. The client root passes them to the client `Provider` by @davesnx
* Router: the server only redirects to a path that starts with a single `/` or to an absolute `http:` or `https:` URL. A loader or route redirect to another target, such as `javascript:alert(1)` or `//evil.example`, renders the page as an internal error, and a server function that redirects there fails. `RouterServer.Adapter.redirectLocation` makes the check for the `Location` header, the RSC redirect envelope and the `Router-Redirect` header by @davesnx

* Router: the client root in the document gets the React key `router:root` next to the `router:ssr` marker, so the two children of `<body>` are keyed by @davesnx
* Router: the client saves the scroll position of each history entry in `sessionStorage` (the 100 most recent entries), also before `updateSearch`, `updateHash` and page unload, and restores it on Back and Forward for content, search-only and hash-only entries, also after a reload or a full page load. A saved position now wins over the hash on Back and Forward by @davesnx

The redirect target takes the place of the history entry the navigation would create. Other redirects load the page in full by @davesnx

## 0.1.0

Initial release of server-reason-react, includes:

- Server-side rendering of ReasonReact components (renderToString, renderToStaticMarkup & renderToLwtStream)
- `server-reason-react.browser_ppx` for skipping code from the server
- `server-reason-react.melange_ppx` for enabling melange bindings and extensions which run on the server
- `server-reason-react.belt` a native Belt implementation
- `server-reason-react.js` a native Js implementation (unsafe and limited)
- `server-reason-react.url` and `server-reason-react.url-native` a universal library with both implementations to work with URLs on the server and the client
- `server-reason-react.promise` and `server-reason-react.promise-native` a universal library with both implementations to work with Promises on the server and the client. Based on https://github.com/aantron/promise
- `server-reason-react.melange-fetch` a fork of melange-fetch which is a melange library to fetch data on the client via the Fetch API. This fork is to be able to compile it on the server (not running).
- `server-reason-react.webapi` a fork of melange-webapi which is a melange library to work with the Web API on the client. This fork is to be able to compile it on the server (not running).
